# 《手写生产级 Agent Harness》行文思路与写作规范

> 本规范是后续所有章节编写的基准。目标是系统性总结从零手写生产级 Coding Agent Harness 的真实工程实践、架构抉择与生产边界防御。
> 拒绝应试背书与概念搬运，只讨论真实工业场景下的高可用、长任务、资损控制与系统韧性。

---

## 一、 定位与工程底色

### 1. 核心定位
这是一份**面向生产系统级落地的硬核工程复盘**。
基线是 `jai-mono` 的真实设计与源码实现，对标 Claude Code / Codex / Pi 等成熟工具的工业级底层（Agent Harness）。

### 2. 核心命题与张力
**“玩具 Demo 只关心如何跑通一次，生产 Harness 90% 的代码都在处理如何体面地停下来、如何防止资损与状态分叉、如何榨干每一分 KV Cache。”**

- **为什么不用重型胶水框架？** 框架把提示词、状态、循环与网络调用绑死，在面对子进程泄露、断电恢复、AST 级权限扫描、精准 Cache 断点时，往往成为阻碍而非助力。
- **奥卡姆剃刀与单一事实源**：不过度抽象，每个模块职责极窄。Durable 存储严格唯一，运行时内存状态可随时抛弃并重建。

### 3. 从 1.md 与 2.md 沉淀出的六大行文法则（写作者自查清单）

1. **同道中人的平视视角（真诚、不装、不爹味）**：
   - 拒绝居高临下的布道姿态（不写“初学者往往不懂”、“面试官一问就露馅”）。
   - 以真实开发者的亲身踩坑展开：“一开始觉得挺简单，但当真正开始写真实任务时，发现差异比预期繁琐得多”。
   - 承认成熟方案的价值（如承认现在的 Vercel AI SDK、LiteLLM 很成熟），讲清楚自己手写封装的特定原因（学习目的、不想带黑盒包袱、要对底层拥有绝对掌控权）。

2. **第一性原理与读者零先验视角（严禁拿着源码倒推文章）**：
   - **假设读者只读过前序章节，从未看过本项目源码**：绝不能在正文中出现读者此时不可能知道的内部参数、后续章节黑话或未声明的字段（例如在第 2 章讲基础主循环时突然冒出 `runFromContext`、`T1/T2`、`EffectEntryReservation`）。
   - **先摆故障现场，再长出代码**：每引入一个数据结构、一个字段、一段辅助函数，必须先让读者看到“如果不加它，原来的最简代码在什么具体场景下会怎么坏掉”。
     - ❌ 错误示范：直接贴出 20 行的 `projectToolCallProtocol` 代码，然后解释“这个函数用来重排消息”。（读者会感到莫名其妙：正常跑循环消息本来就是配对的，为什么要重排？）
     - ✅ 正确示范：先讲用户中途插话（Steering）或按 ESC 取消第 2 个工具时，消息数组变成了 `assistant(toolCall x2) -> toolResult(1) -> user`，直接发给 Anthropic 会报 400 错误；为了解决这个错位，才需要在发请求前加一道配对重排。
   - **代码切片做减法（善用 `// ...` 省略次要细节）**：展示源码时，主动剥离属于后续章节的横切关注点（如崩溃恢复钩子、测试桩）以及样板式的变量声明、重复的 `emit` 调用，用 `// ...` 代替，每个代码块控制在 15 行左右，只保留当前推导步最核心的几行逻辑。

3. **用真实数据说话，实测切片先行（抓包先于理论）**：
   - 讲协议差异，不要抽象罗列文字，直接上真实请求与响应 JSON / SSE 抓包对比。
   - 用同一个测试用例（如统一传入 `get_weather(city: "Shenzhen")` 工具、问同一句话），横向拉通 OpenAI、Anthropic、Responses 等协议。
   - 关键对比点必须一目了然（如参数是已解析的对象还是未解析的字符串、停止原因的名字、工具块在一等公民内容还是旁路字段）。

4. **严格遵守调用者的“因果链条”（拒绝空降技术名词）**：
   - 严禁在未交代业务矛盾前突然扔出一个孤立的类或设计（如突然扔出 `class EventStream` 或直接甩出一棵 20 行的生命周期事件树）。
   - 永远顺着一次调用或一个状态机从简到繁的生长过程推进：
     1. **最简原型与矛盾**：最朴素的写法（如 `while (true)`）长什么样？为什么在真实场景下不够用？
     2. **入口契约**：为了解决黑盒与状态污染，上层最期望面对的纯净接口长什么样？
     3. **核心流转**：顺着数据进入、处理、派发、退出的真实顺序，一步步长出完整设计。
      4. **异常边界兜底**：当出现网络中断、模型违规、工具卡死时，最后一道防线怎么做。

5. **工程考量与产品视角并重（不仅仅是技术报错）**：
   - 不仅要讲技术实现，更要讲背后的“产品体验权衡”。
   - 典型如多模态降级：纯文本模型报错不仅仅是抛个 400 给用户，从 Agent 产品角度看，不能让用户去纠结“我是不是要换模型”，而应该由 Agent 优雅降级并在会话中明确告诉用户当前模型没有视觉能力。
   - 典型如工具报错：工具参数传错或文件不存在时，不能直接 throw 让整个 Agent 循环崩溃退出，而应该包装成 `isError: true` 的工具结果喂回给模型，因为绝大多数普通错误模型看到报错后自己就能修好。

6. **权威背书与一手考据链接**：
   - 观点必须有权威出处（如引用 Armin Ronacher 的 *Agent Design Is Still Hard*、Pi 的设计哲学）。
   - 凡涉及容易引起争议的协议规范（如 `stream_options.include_usage`、`max_completion_tokens`、Anthropic 的 4 个断点上限），必须附带一手官方文档链接。
   - 凡提到自己项目实现，必须附带本仓库的 GitHub 源码链接，确保结论可复核。

- **严禁使用浮夸比喻与冗长修辞标题（标题与用词必须克制、直接）**：
  - ❌ **绝对不要使用小说化、戏剧化比喻**：拒绝“走出 while(true) 的玩具陷阱”、“退出的艺术”、“三道绝对刹车线”、“现实的毒打”等情绪化修饰。
  - ✅ **标题与小节直陈技术本质**：直接说明“讨论什么模块、处理什么具体问题”。例如：“`02. Agent Loop 核心流转与生命周期控制`”、“`单层状态机与原子 Turn 推进`”、“`终止条件判定：自然终态、取消与最大轮次`”。
  - ✅ **正文叙述冷静客观**：用“轮次超限保护”代替“硬顶防线”，用“进程取消清理”代替“孤儿清理杀手锏”，不煽情、不搞冲突对立。

## 二、 单篇标准四段式结构（Chapter Blueprint）

每一章抛弃应试套路，直接聚焦于一个具体的工程子系统，按以下四步展开：

```
[1. 生产痛点与边界定义]
真实共鸣场景 / 现实工程瓶颈 -> 明确该子系统要解决的不可妥协约束
       ↓
[2. 真实抓包对比与心智模型]
用同一个真实 Case 暴露底层差异（实测 JSON / SSE 切片对比） -> 建立领域直觉
       ↓
[3. 核心设计与因果推导]
严格顺着生命周期因果链（入口契约 -> 入向抹平 -> 出向双模 -> 终态防伪）展开代码切片
       ↓
[4. 生产级故障防御与权衡]
深水区 Corner Cases（参数打架、进程脱管、协议伪造、缓存击穿、状态分叉）与防线实现
```

---

### 第 1 节：生产痛点与边界定义（Problem & Motivation）
- **核心任务**：建立同行共鸣与反差感。
- **范式**：
  - 借用真实的开源社区讨论（如 Chasen 路线、Armin 博客、Pi 讨论）切入；
  - 诚实陈述“我原本以为这事很简单”，接着列出 3~4 个实际写代码必然踩中的痛点；
  - 点题：为什么不能在业务主流程里写 `if-else`，为什么必须独立分层。

### 第 2 节：真实抓包对比与心智模型（Empirical Evidence）
- **核心任务**：用一手抓包证据说话，不凭空推断。
- **范式**：
  - 设计一个标准最小用例（例如带同一个工具函数的问答）；
  - 逐一展示各主流协议的真实返回，指出结构特点（字段层级、数据类型、状态原因、流式切片方式）；
  - 用小结对比表格或清单清晰标明差异，让读者立刻产生“确实需要一套机制收敛它们”的紧迫感。

### 第 3 节：核心设计与因果推导（The Engine Room）
- **核心任务**：顺着调用者的生命周期推导代码，杜绝空降。
- **行文四部曲**：
  1. **入口契约**：上层业务最自然、最干净的调用姿势是什么？（给出纯净 Context，没有任何 vendor 污染）。
  2. **入向组装（Inbound）**：离开本地前必须抹平哪些隐形差异？（参数更名、工具 Schema 适配、多模态安全降级、KV Cache 物理断点自动排版）。
  3. **出向接收（Outbound）**：面对异步或流式碎片，UI 与 Agent 状态机的核心矛盾是什么？顺理成章引出双模流（如 EventStream：既能 `for await` 实时消费，又能 `await stream.result()` 获取完整消息）。
  4. **终态安全**：拿到结果后的最后一道防线（如协议假调用拦截、脏数据清洗）。

### 第 4 节：生产级故障防御与权衡（Edge Cases & Defenses）
- **核心任务**：深入 2~3 个只有长任务真实运行才会踩到的硬核隐患。
- **三要素**：
  - **故障现场（Failure Mode）**：死锁、内存爆裂、脏写入、进程脱管、非原生协议注入。
  - **根因剖析（Root Cause）**：操作系统的进程模型差异、网络流式分块截断、模型输出漂移。
  - **系统级防御（Systemic Defense）**：在核心基础设施层单点封堵，杜绝散弹式打补丁。

## 三、 全书章节架构（自底向上的系统工程）

1. **`00. 模型抽象层与流式基座 (packages/ai)`**
   - 跨 Provider 协议碎片化抹平与流式增量事件归一化
   - 工业级 KV Cache 三级断点自动化排版
   - 非原生伪造 ToolCall 协议防御与 Thinking 签名透传
2. **`01. Agent Loop 核心流转与生命周期控制 (packages/agent)`**
   - 不可变运行时上下文与原子 Turn 推进
   - 协作式取消（`AbortSignal`）、硬步数预算与终态仲裁
   - 工具调用参数强校验与并行/串行批次调度
3. **`02. 上下文工程、KV Cache 断点与后台投机压缩`**
   - 缓存友好（Cache-Friendly）的消息排布：Prefix 稳定性原则
   - 基于 Token 预算的成对截断切点推导
   - 消除等待的投机性后台压缩（Speculative Compaction）
4. **`03. 权限系统、Bash AST 静态分析与审批拦截 (packages/coding-agent)`**
   - 正则字符串匹配的致命死角（Wrapper、环境变量前缀、别名）
   - 基于 `tree-sitter-bash` 的命令树展开与平铺
   - 物理路径逃逸校验（Symlink）与安全执行模式
5. **`04. 树形 Journal、T1/T2 效果边界与崩溃恢复`**
   - 单一事实源：Append-Only 树形 Journal 与不可变 Entry
   - 外部副作用的两阶段边界：T1 意图落盘 vs T2 结果落盘
   - 崩溃自愈：针对 `indeterminate_tool`（未决操作）的纯函数恢复 Reducer
6. **`05. 执行环境、Kill Boundary 竞态与 OOM 熔断`**
   - 异步取消下的孤儿进程泄漏与 POSIX 进程组硬杀（Kill Boundary）
   - 大文件 IO 熔断与输出尺寸硬限制
7. **`06. 控制面解耦、Director 调度栈与 Steering 打断`**
   - 复杂长任务下的控制冲突与死锁
   - Director 责任链栈：Plan 模式、Todo 推进与控制权交还
   - Steering（抢占式插话）与 Follow-up（队列排队）调度
8. **`07. Skills 级联、MCP 传输层与 ToolCatalog 二阶段`**
   - 工具 Schema 膨胀与 Attention Tax 抑制
   - MCP 多传输层自愈与 `tools/list_changed` 动态更新
   - ToolCatalog 二阶段检索：动态换取 opaque `toolRef`
9. **`08. 单向状态投影、推测流渲染与 PTY 逻辑行缓冲 (Desktop / UI)`**
   - UI 作为只读投影，禁止状态反写污染
   - 历史消息冷冻结 + 尾部增量推测流渲染
   - PTY 逻辑行账本（Logical Rows）规避缩放重影与 ANSI 乱码
10. **`09. 工业级评测体系与全链路可观测性`**
    - 评测分层：纯函数状态机 -> 故障注入 -> 任务沙箱
    - 全链路追踪元组（`operationId` -> `attemptId` -> `toolCallId`）
    - Cache 命中率、TTFT 与长链路归因分析

## 四、 开篇行文范例（语调对照参考）

在动笔写具体章节引言时，以此语调为基准，时刻对照自查：

> ❌ **反面范例（爹味、装懂、网梗乱飞）**：
> “很多初级开发者以为调个 API 就叫 Agent 了，第一步就直接被各家供应商按在地上摩擦。面试官一问底层你就露馅，今天我就来教你们为什么 90% 的人写的都是垃圾玩具……”
>
> ✅ **正面范例（客观陈述、平静、说具体事实、少比喻）**：
> “前几天看到 @chasen_liao 发的那篇学习路线，里面第一部分就提到了‘先把一次模型调用看明白’。
> 我在写 `jai-mono` 最开始的时候，也以为只要装上 `openai` 和 `@anthropic-ai/sdk`，把请求发出去拿到结果，第一步就算完成了。
> 但实际接入真实编码任务时，底层的接口差异比预想的要繁琐得多：各家的流式 chunk 结构各不相同，工具调用参数会被拆碎成多个片段；带思考过程的模型在多轮对话中需要校验特定的签名字段；Anthropic 的 Prompt Cache 需要严格在固定位置标记断点，稍有不一致就会失去缓存效果。
> 如果直接在 Agent Loop 内部处理这些细节，主循环里很快就会堆满针对不同厂商的分支判断。
> 这篇笔记主要复盘 `packages/ai` 这个包的设计：如何把不同模型的流式事件、工具调用拼装、缓存断点注入和参数兼容规则统一收敛到一层，给上层提供一个确定、稳定的调用接口。”
